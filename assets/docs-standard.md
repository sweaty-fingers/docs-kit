# 문서 규격

docs-kit을 쓰는 프로젝트의 문서를 **어떤 종류로 나누고, 각 종류에 무엇을, 어떤 형식으로 쓰는지** 정한 규격입니다. 사람과 에이전트가 문서를 새로 쓰거나 고칠 때 이 페이지를 기준으로 삼습니다.

> 규격 버전: docs-kit의 `VERSION` (1.0 전, 초기 단계). 1.0 전까지는 실제 프로젝트에서 써 보며 고치고, 고칠 때마다 CHANGELOG와 기존 문서 이전을 함께 합니다(§12). 이 규격을 쓰기로 한 이유는 각 프로젝트의 ADR에 둡니다. 프로젝트마다 쓰는 탭(메뉴)은 고를 수 있습니다(§13).

---

## 1. 문서의 층

문서는 **무엇을 담는가**로 네 층에 나눕니다. 한 문서는 한 층에만 속합니다.

| 층 | 답하는 질문 | 문서 종류 | 바뀌는 방식 |
| --- | --- | --- | --- |
| **발행물** | 이 독자에게 한 편의 글로 무엇을 전하나 | 발행물 P (개요, 보고서, 릴리스 노트, 해설, 발표), 주간 보고 | 개요는 갱신, 나머지는 발행 후 고정 |
| **정본** | 무엇을, 왜 이렇게 만드나. 해 보니 어땠나 | arc42 섹션 A1~A12, ADR, 실험 기록 EXP, 검증 기록 VR, 모델 카드 MC | 섹션은 갱신. ADR·EXP·VR·MC는 추가만 |
| **운영** | 어떻게 하나. 값이 무엇인가. 지금 어느 버전을 쓰나 | 실행 가이드 G, 참고 R, 공용 파일 목록 | 갱신 |
| **지식** | 알아야 할 배경 | 배경(부록 A), 용어집(A12) | 가끔 갱신 |

**사실은 정본에만** 둡니다. 발행물·운영 문서에 새 사실이나 결정이 생기면 먼저 정본에 넣고, 그 문서는 정본을 인용하거나 링크합니다.

**할 일은 문서가 아니라 이슈 트래커**(GitLab 이슈 등)에 둡니다. 문서에 할 일 목록(체크리스트)을 만들지 않습니다. 할 일과 진행 상태는 담당·기한·알림이 있는 트래커가 맡고, 문서는 무엇을 왜 하는지와 결과를 맡습니다(§9). 예외는 **로드맵**(§5.3) 하나입니다. 로드맵은 업무 단위의 큰 흐름(무엇 다음에 무엇, 갈래가 언제 만나나)만 보여 주고, 세부 할 일은 이슈로 링크합니다.

## 3. arc42 섹션 (정본)

arc42는 아키텍처 문서에 **무엇을** 쓸지 정한 12개 섹션이고, C4는 구조를 **어떻게** 그릴지 정한 표기법입니다. 섹션 번호와 이름은 고정이고, 내용은 필요할 때 채웁니다. 연구를 겸하는 프로젝트는 "연구 과제에서 더 담는 것"을 같은 섹션에 둡니다.

| 섹션 | 담는 것 | 연구 과제에서 더 담는 것 | 그림 | 여기 두지 않는 것 |
| --- | --- | --- | --- | --- |
| **A1. 목표와 요구사항** | 과제 목표, 주요 요구사항, 이해관계자(팀·역할), **품질 목표 3~5개** | **연구 질문(RQ)과 가설**, 성공 기준의 요약, 단계와 산출물(로드맵) | — | 실험 설계 상세 (→ 부록 B) |
| **A2. 제약** | 바꿀 수 없는 기술·조직 조건 (주어진 하드웨어, 플랫폼, 규정, 일정, 다른 팀 의존) | 데이터·장비 접근 제약, 윤리·안전 제약 | — | 우리가 고른 것 (→ A4, ADR) |
| **A3. 컨텍스트와 범위** | 시스템 경계, 외부 사용자·시스템, **외부 인터페이스 표**(무엇을, 어떤 규격으로) | 다른 팀과의 책임 경계, 데이터를 주고받는 계약 | **C4 Context** | 내부 구조 (→ A5) |
| **A4. 해결 전략** | 근본 선택의 요약: 구조 원칙, 핵심 기술, 품질 목표를 어떻게 달성하나 | 연구 접근 전략 (병렬 트랙, 대리 모델로 먼저 진행 등) | — | 결정 하나하나의 근거 (→ ADR) |
| **A5. 빌딩 블록** | 컨테이너·모듈 구성과 책임, 저장소 구조, 주요 컴포넌트 | 모델 구조(정책, 인코더, 어댑터)의 블록 | **C4 Container**, 필요한 컨테이너만 **Component** | 실행 순서 (→ A6) |
| **A6. 런타임** | 아키텍처적으로 중요한 **시나리오 2~5개**의 실행 흐름 | 학습·재학습 루프, 데이터 기록 → 학습 흐름, 모델 교체 절차 | 동적 그림 (C4 dynamic 또는 Mermaid 시퀀스) | 모든 시나리오 |
| **A7. 배포** | 실행 환경(장비, 서버, 개발 PC), 무엇이 어디서 도는가, 배포 경로, 환경별 차이 | 학습 인프라, 데이터·결과 보관소 | 배포 그림 (C4 deployment 또는 Mermaid) | 배포 명령 (→ 실행 가이드) |
| **A8. 횡단 개념** | 여러 블록에 걸친 규칙과 개념: 데이터 모델, 인터페이스 계약, 시간·동기화, 오류·안전, 버전 고정·재현성, 개발 환경 규칙 | 데이터 원본·파생본, 시뮬레이션 자산, 실험 재현 규칙 | 필요하면 | 한 블록에만 해당하는 것 (→ A5) |
| **A9. 결정** | ADR 목록(자동)과 읽는 순서 | 연구 방향 결정도 ADR로 | — | ADR 본문 (→ `docs/adr/`) |
| **A10. 품질 요구사항** | 품질 시나리오(자극 → 응답 → 측정 기준), **수용 기준** | **평가 프로토콜**(지표, 시행 횟수, 초기 조건, 성공 기준, 통계), 모델 검증 기준 | — | 실제 결과 (→ EXP, VR) |
| **A11. 리스크와 기술 부채** | 알려진 리스크·부채의 **통합 목록**(영향, 가능성, 대응, 담당, 상태) | 연구 리스크(가설 실패, 데이터 부족, 다른 팀 지연) | — | 다른 문서에 흩어진 리스크 목록 |
| **A12. 용어집** | 모든 용어의 한 줄 뜻과 설명 위치 (`docs/glossary/`) | — | — | 다른 문서의 용어 표 |

### 3.1 섹션 페이지 형식

| 항목 | 규칙 |
| --- | --- |
| 파일 | `docs/arc42/aNN_<영문 이름>.md` (예: `a03_context.md`). 12개 모두 둠 (비어 있어도) |
| 제목 | `# A<N>. <제목>` (예: `# A3. 컨텍스트와 범위`) |
| 머리말 | `arc42: <N>`, `status`, `owner`, `reviewed`(마지막으로 내용을 확인한 날), `c4_views`(넣을 C4 뷰 id, 선택), `summary`(지금 들어 있는 것 한 줄, 선택. 섹션 현황표에 표시) |
| `status` | `empty`(아직 안 씀) · `partial`(일부) · `stable`(현재와 맞음) · `n/a`(이 프로젝트에 필요 없음, 이유 한 줄) |
| 본문 | ① 요약 2~5줄 → ② 번호 절(`## 1. ...`) → ③ "관련 결정·검증" (ADR, VR 링크) |
| 빈 섹션 | `status: empty`와 "무엇이 들어갈 예정인지" 한 줄. 억지로 채우지 않음 |

## 4. 연구 부록

arc42에 없는, 연구에 필요한 정본입니다. 번호(A~D)와 위치는 고정입니다.

| 부록 | 위치 | 단위 | 담는 것 |
| --- | --- | --- | --- |
| **A. 배경** | `docs/background/` | 주제 하나 | 배경 지식, 관련 연구 조사, 도구 설명. 원본 지식이라 발행물이 아님 |
| **B. 실험 (EXP)** | `docs/experiments/NNNN-*.md`, 제목 `# EXP-NNNN.` | **연구 질문·가설 하나** | 가설(RQ 번호), 설정, 실행 목록(실행 ID), 결과 표, **실패 서술**, 통계, 결론, 다음 단계. 실패·부정 결과도 남김. 결론이 결정이면 ADR로 |
| **C. 검증 (VR)** | `docs/records/NNNN-*.md`, 제목 `# VR-NNNN.` | **판정 하나** | 미리 정한 기준(A10 등)에 대한 통과·불통과, 증거, 재현(`repro.sh`, `expected.txt`). 환경·빌드 검증과 **고른 모델 후보의 검증** |
| **D. 모델 (MC)** | `docs/models/NNNN-*.md`, 제목 `# MC-NNNN.` | **승격된 모델 하나** | 용도, 학습 데이터, 근거 VR, 한계, 배포 위치 |

```text
실행(run) ──모두──▶ EXP ──후보 선정──▶ VR ──통과──▶ MC ──▶ 배포(A7)
 추적 도구·보관소     질문 하나 = 문서 하나   A10 기준 판정      승격된 모델
 (문서로 쓰지 않음)   (실패도 남김)         (고치지 않음)
```

- 실행(학습·평가 1회)은 문서로 쓰지 않습니다. 실험 추적 도구와 보관소에 두고 EXP가 실행 ID로 가리킵니다.
- EXP 형식은 [실험 템플릿](experiments/template.md)(머리말 `status`, `started`, `by`, `area`, `question`, `adr`, `issues`)이고, [실험 목록](experiments/list.md)은 머리말에서 자동으로 만들어집니다. MC의 상세 형식은 첫 모델을 승격할 때 추가합니다.
- 모델 검증 VR의 결과 표에는 실행 횟수, 초기 조건, 성공 기준, 실패 서술, 통계를 넣습니다.

## 5. 발행물 (문서함)

정본을 엮어 **특정 독자에게 한 편의 글로** 전하는 문서입니다.

| 항목 | 규칙 |
| --- | --- |
| 파일 | `docs/publications/NNNN-<영문 제목>.md`, 제목 `# P-NNNN. <제목>` |
| 머리말 | `kind`, `audience`, `date`, `status`(draft · published · archived), `based_on`(엮은 정본 `[A1, A3, ADR-0004, VR-0002, G2]`), 스냅숏이면 `commit` |
| `kind` | `overview`(살아 있는 개요) · `report`(보고서) · `release`(릴리스·배포 노트) · `note`(주제 해설) · `slides`(발표) |

| 종류 | 성격 | 규칙 |
| --- | --- | --- |
| **overview** | 늘 최신 (예: 과제 공통 설계 가이드, 팀 계획 개요) | 짧은 서술 + 정본 링크. 꼭 같아야 하는 표는 정본에서 끼워 넣음 |
| **report, release, note, slides** | 그 날짜의 스냅숏 | `date`, `commit`을 적고 **발행 후 고치지 않음**. 새 판은 새 번호. 웹에서는 "스냅숏" 안내가 자동으로 붙음 |

### 5.1 정본 끼워 넣기

정본 쪽에 표시를 하고 발행물에서 그 이름으로 불러옵니다(끼워 넣기, MkDocs 판의 `pymdownx.snippets`와 같은 문법). 표시는 HTML 주석이라 정본 페이지에는 보이지 않습니다.

````markdown
<!-- 정본: docs/arc42/a01_goals.md -->
<!-- --8<-- [start:rq] -->
| RQ | 질문 | 가설 |
| --- | --- | --- |
<!-- --8<-- [end:rq] -->

<!-- 발행물 -->
;--8<-- "arc42/a01_goals.md:rq"

자세한 근거: [A1 §1](../arc42/a01_goals.md#1-...)
````

- 위 예시처럼 문서 안에서 끼워 넣기 줄을 **설명용으로 보여 줄 때**는 앞에 `;`를 붙입니다(`;--8<-- ...`). 붙이지 않으면 실제로 끼워 넣으려다 빌드가 실패합니다.
- 끼워 넣기는 **웹에서만** 동작하고 GitLab 화면에서는 `--8<--` 줄이 그대로 보입니다. 끼워 넣는 곳마다 정본 링크를 함께 둡니다.
- 꼭 같아야 하는 표·목록에만 씁니다. 나머지는 요약과 링크로 씁니다.

### 5.3 로드맵

한 일과 할 일을 업무 단위로 한 그림에 보입니다(메뉴 "로드맵", 편집 안내는 그 메뉴 안).

| 항목 | 규칙 |
| --- | --- |
| 파일 | `docs/roadmap/roadmap.yml` 하나. 그림, 업무별 흐름, 표, 항목 페이지는 빌드할 때 만들어짐 |
| 담는 것 | 업무(마일스톤) 단위의 일과 그 순서(`after`), 갈래(트랙), 상태. 세부 할 일은 이슈로 두고 `refs`로 링크 |
| 앞으로 할 일 | 날짜 대신 확신 정도(`next`, `later`, `future`). 계획이 바뀌면 상태와 `after`만 고침 |
| 끝난 일 | `status: done`과 끝난 날. 근거(VR, ADR, MR)를 `refs`에 |
| 고치는 때 | 일을 마치거나 계획이 바뀐 커밋에서 함께 |

### 5.4 문서 지도

모든 문서를 점으로, 관련된 문서를 선으로 이은 지도입니다(메뉴 "문서 지도"). 빌드할 때 자동으로 만들어지고 따로 쓰는 파일은 없습니다.

| 선 | 근거 |
| --- | --- |
| 본문 링크 | 렌더된 본문의 링크(방향 있음, 백링크도 봄) |
| 머리말 관계 | VR `adr`·`guide`·`supersedes`, ADR `related`·`supersedes`, 실험 `adr`, 발행물 `based_on` |
| 비슷한 내용 (제안) | 본문 낱말(TF-IDF), 같은 문서를 가리키는 정도, 같은 C4 구성요소. 링크가 없는 쌍만, 이유와 함께 |

**주제**가 지도를 모읍니다. 주제 목록은 로드맵 트랙(`roadmap.yml`의 `tracks`)과 공통(`common`)이고, 문서마다 최대 2개(첫째가 주 주제)를 아래 순서로 정합니다.

| 순서 | 어디서 | 쓰는 곳 |
| --- | --- | --- |
| 1 | 머리말 `topics: [core, ui]` | 새로 쓰는 문서 |
| 2 | `docs/graph/topics.yml` (`ADR-0003: [core]`, `G2: [core, ui]`, docs 경로) | 쓴 뒤 고치지 않는 ADR·VR, 확인한 추정 |
| 3 | 로드맵 항목의 `refs` | 자동: 그 항목의 트랙 |
| 4 | 이웃 문서에서 추정 (추정 표시) | 자동: 점검에 올라옴 |

지도 패널의 **점검**(이어지지 않은 문서, 주제가 추정된 문서, 주제와 연결이 어긋나는 문서, 링크를 걸면 좋을 쌍)을 보고, 맞는 제안은 본문에 링크로 넣습니다. 그래서 링크와 머리말 관계를 정확히 쓰는 것이 지도를 좋게 만드는 방법입니다.

### 5.5 현황판

과제의 계획 작업량 대비 진척과 예측, 단계별 통과 기준과 일의 분해, 연구 질문, 리스크를 한 페이지에 보입니다(메뉴 "현황판", 편집 안내는 그 메뉴 안). 연구 과제라 계획이 바뀌는 것을 전제로 합니다. 작업량(scope)은 계획에 든 일의 크기 합, 폭은 먼 일의 최소~최대 크기입니다.

| 항목 | 규칙 |
| --- | --- |
| 파일 | `docs/plan/scope.yml`(단계와 일의 분해, 연구 질문), `docs/plan/risks.yml`(리스크 대장), 선택으로 `docs/plan/issues.json`(이슈 상태 스냅숏). 그림·표·트리는 빌드할 때 만들어짐 |
| 일의 분해 | Epic(단계) > Feature > Story > Backlog(이슈) > WBS(작업 묶음). 평평한 목록 + `parent`. 크기는 포인트, 먼 일은 폭 `[최소, 최대]`(연동 계획). 페이지에서는 단계마다 통과 기준 아래에 펼쳐짐 |
| 완료 정의 | Epic은 단계 통과 기준(`met`, `evidence`), 백로그·WBS는 끝났다고 말할 조건. 팀 공통은 `team_dod` |
| 상태 | 따로 적지 않고 로드맵 항목(`roadmap:`)이나 이슈(`issue:`)에서 가져옴. 둘 다 없는 일만 `status` |
| 계획 변경 | 항목을 지우지 않고 `added` / `removed` + `reason`. 계획을 크게 다시 정한 날은 `baselines` |
| 스프린트 | 짧은 주기(기본 7일)로 일을 계획하고 마감 때 약속·끝냄·이월·회고를 남김. `docs/plan/sprints.json`, 보드 `plan/board/`(개발 미리보기에서 끌어 옮기면 저장 서버 `.docs-kit/bin/serve.sh board`가 씀). 진척은 그대로 근거(로드맵·이슈)로 셈 |
| 리스크 | 리스크는 이 대장 한 곳에. 가능성·영향(1~5)은 `history`에 줄을 더해 바꿈(추이). arc42 A11은 `<!-- risk-register -->`로 같은 표를 보임 |
| 고치는 때 | 일을 마치거나 계획이 바뀐 커밋에서 함께, 리스크 재평가와 이슈 스냅숏은 주간 보고 때 |

### 5.6 근거 점검

문서의 검증할 수 있는 주장을 원천과 맞춰 할루시네이션과 낡은 근거를 찾는 페이지입니다(메뉴 "근거 점검"). 빌드할 때마다 다시 잽니다.

| 항목 | 규칙 |
| --- | --- |
| 도구 | 문서 검색 `bin/docs_search.py`(절 단위, BM25 + 한국어 글자 2-gram, 대체된 기록 표시), 근거 점검 `bin/docs_check.py`(`--changed`: 바뀐 문서만, `--record`: 날짜별 기록). 표준 라이브러리만, 사내망 밖으로 보내는 것 없음 |
| 판정 | 틀림(가리킨 문서·이슈·경로·포트가 없음), 확인 못 함(코드·원 출력·VR에서 못 찾은 이름·옵션·수치, 계획된 경로), 낡음(대체된 기록만 인용, 코드가 문서보다 나중에 바뀜) |
| 파일 | `docs/quality/config.json`(외부·계획 경로, 포트 표 `ports_doc`, 모델 서버 시작 안내 `embed_start`·`llm_start`, 질문 서버 `ask`), `questions.json`(검색 평가), `history.json`(추이), `incidents.json`(사례) |
| 쓰는 때 | 문서를 고친 뒤 `--changed`로 틀림 0, 주간 보고 때 `--record`. 기록 문서(ADR·VR·주간 보고)는 고치지 않고 새 문서로 바로잡음 |

### 5.2 주간 보고

팀 회의에서 보는 진행 보고입니다. 발행물의 한 종류지만 자주 쌓이므로 번호(P-NNNN) 대신 날짜로 이름을 짓고 메뉴를 따로 둡니다. **지난 보고를 쓴 날부터 이번 보고를 쓴 날까지**를 **업무(이슈 트래커 마일스톤) 기준**으로 씁니다. 날짜별로 쓰면 한 업무의 이야기가 여러 주에 흩어지므로, 업무 이름을 매 보고 같게 두고 "업무별 흐름" 페이지가 그것을 한 줄기로 모읍니다.

| 항목 | 규칙 |
| --- | --- |
| 파일 | `docs/weekly/YYYY-MM-DD.md` (쓴 날), 제목 `# YYYY-MM-DD 주간 보고` |
| 머리말 | `date`, `from`(지난 보고의 `date`, 첫 보고는 프로젝트 시작일), `status`(draft · published), `by`, 발행하면 `commit`, 선택 `meeting` |
| 업무 이름 | 마일스톤이 있으면 그 이름, 없으면 정한 이름을 매 보고 같게 (업무별 흐름이 이름으로 모음) |
| 본문 | 1 요약, 2 지난 회의 요청사항(이슈 번호와 상태), 3 업무별 진행(`### 3.N <업무 이름>`마다 **배경**, **한 일**, **결과**, **다음**, 선택 **막힌 것**), 4 정할 것과 도움 필요, 5 회의 메모 |
| 사실 | 새 사실·결정은 쓰지 않음. 결과는 정본·작업 내역에 먼저 두고 링크 |
| 고치기 | `draft`일 때 자유롭게. 회의 뒤 `published` + `commit`, 그 뒤에는 회의 메모만 덧붙임 |

## 9. 공통 작성 규칙

| 규칙 | 내용 |
| --- | --- |
| 링크 | 문서 사이는 `.md` 상대 경로. `docs/` 밖 파일은 링크 대신 코드 경로(`` `tools/x.sh` ``) |
| 절 참조 | 같은 문서 `§4.3`, 배경 문서 `01 §4`, arc42 `A5 §2`, 가이드 `G1 §6`, 참고 `R2 §1`은 텍스트로 써도 웹에서 링크됨(GitLab 화면에서는 텍스트). ADR·VR·P와 GitLab에서도 눌러야 하는 곳은 직접 링크 |
| 제목 | 번호로 시작(`## 4. ...`, `### 4.3 ...`). 링크될 제목에 ` / `, ` → `, ` - ` 쓰지 않음 |
| 문체 | "~합니다"체. 사실과 추정을 구분하고, 확인하지 않은 것은 "확인하지 않음"이라고 씀. 숫자·버전에는 출처 |
| 날짜 | `YYYY-MM-DD`. 상대 표현("어제", "지난주") 쓰지 않음 |
| 목록 | 하위 목록은 한 단계에 4칸 들여쓰고, 목록 앞에는 빈 줄을 둠(Markdown 처리기의 규칙). 2칸으로 쓰거나 글 바로 아래 붙여 써도 사이트에서는 키트가 바로잡아 보여 주지만, GitLab 화면 등 다른 곳과 맞추려면 4칸 + 빈 줄로 씀 |
| `> 기준:` 줄 | 날짜와 **마지막 검증 VR 링크**만. 결과를 길게 쓰지 않음 |
| 용어 | 새 용어는 용어집 색인에 한 줄. 다른 문서에 용어 표를 만들지 않음 |
| 큰 파일 | 수 MB를 넘거나 바이너리 결과는 저장소 밖 보관소에 두고, 문서에는 경로·크기·sha256 |
| 할 일 | 이슈 트래커에. 문서에는 이슈 번호(`#12`)만. 결정이 필요한 항목은 결정 라벨 이슈 + A11 "열린 질문"에서 링크, 정해지면 ADR을 쓰고 닫음. ADR "후속 작업"과 VR "남은 문제"는 짧게 쓰고 이슈 번호를 붙임 |
| 새 문서 | ADR·VR·arc42·발행물은 메뉴와 목록이 자동. 켠 탭의 폴더(가이드, 참고, 배경 등)에 둔 문서도 메뉴에 자동. 탭 폴더 밖의 문서만 `docs-kit.yml` `nav`에 추가 |

- **0.x (지금)**: 프로젝트에서 써 보며 고칩니다. 바꿀 때는 docs-kit의 이 페이지와 템플릿·훅을 함께 고치고, `VERSION`, `CHANGELOG`를 올리고, 기존 문서를 새 형식으로 옮깁니다(내용은 바꾸지 않음).
- **1.0 고정 조건**: 한 프로젝트에서 A1·A3·A5·A9·A10·A11이 `partial` 이상이고, 다른 프로젝트 하나에 적용해 섹션·부록 구성이 맞는 것을 확인했을 때.
- **1.0 이후**: 섹션 번호, 부록, 문서 종류, 머리말 필드는 고정. 바꾸려면 메이저 버전과 이전 안내를 냅니다.

## 13. 탭 고르기 (프로젝트 성격별)

docs-kit은 모든 탭의 기능과 템플릿을 갖고 있고, 프로젝트는 그중 **쓸 탭만 켭니다**. 설정은 프로젝트 루트의 `docs-kit.yml` 한 파일입니다.

```yaml
profile: dev          # 시작 묶음: minimal | app | dev | research | all
features:             # 묶음에서 바꿀 탭만: true 켬, false 끔
  experiments: true
areas:                # ADR·VR·EXP 머리말 area 값 (id: 이름)
  dev-env: 개발 환경
```

| 하는 일 | 명령 |
| --- | --- |
| 지금 켜진 탭 보기 | `.docs-kit/bin/kit.py status` |
| 탭 켜기 (시작 파일도 복사, 있는 파일은 그대로) | `.docs-kit/bin/kit.py enable plan roadmap` |
| 탭 끄기 (문서는 남고 메뉴에서만 빠짐) | `.docs-kit/bin/kit.py disable weekly` |
| 묶음 바꾸기 | `.docs-kit/bin/kit.py profile research` |

- **새 탭이 필요해지면 새로 만들기 전에** 아래 표에서 같은 일을 하는 탭이 있는지 보고 켭니다. 없을 때만 docs-kit에 새 탭을 만듭니다(모든 프로젝트가 함께 씀, §12).
- 켠 탭은 메뉴에 저절로 들어가고 순서는 §2를 따릅니다. 끈 탭의 템플릿 페이지는 메뉴 밖에서 그대로 열리므로 링크가 끊기지 않습니다.
- `docs-kit.yml`이 없는 프로젝트는 `docs/`에 폴더가 있는 탭만 켭니다(이전 방식).

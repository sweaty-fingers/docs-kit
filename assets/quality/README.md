# 근거 점검

문서에 적힌 **검증할 수 있는 주장**(문서 번호, 이슈, 코드 경로, 명령·옵션, 포트, 식별자, 수치, 인용한 기록)을 하나씩 원천(저장소 파일, VR 원 출력, 이슈 스냅숏, 포트 표)과 맞춰 봅니다. 사람이나 에이전트가 **없는 것을 있다고 쓴 것(할루시네이션)**과 **근거를 잃은 것(문서 낡음)**을 찾아 고칠 일로 바꾸는 페이지입니다. 문서를 빌드할 때마다 다시 잽니다.

??? info "무엇을 재고, 무엇을 재지 못하나"

    - **틀림**: 가리킨 것이 원천에 없습니다(없는 파일·문서 번호·이슈·포트). 할루시네이션이거나 옮겨진 뒤 고치지 않은 것입니다.
    - **확인 못 함**: 있어야 할 곳에서 못 찾았습니다(코드에 없는 이름, 원 출력에 없는 수치). 틀렸다는 뜻은 아니고 사람이 확인할 대상입니다.
    - **낡음**: 대체된 기록만 인용하거나, 가리키는 코드가 문서보다 나중에 바뀌었습니다.
    - 방식은 FActScore처럼 글을 **원자 단위 주장**으로 쪼개 원천과 대조하는 것이지만, 언어 모델 대신 결정적인 규칙으로 판정하므로 결과가 재현됩니다. 대신 **문장의 뜻**(예: "A가 B보다 빠르다")은 재지 못합니다. 그런 주장은 VR·EXP를 링크하는 규칙(문서 규격)과 아래 **검색 평가**, **사례 기록**으로 다룹니다.
    - 에이전트는 작업 전에 문서 검색(`python3 .docs-kit/bin/docs_search.py "질문"`)으로 근거를 먼저 찾고, 문서를 고친 뒤 `python3 .docs-kit/bin/docs_check.py --changed`로 틀림 0을 확인합니다.

## 검색 평가

에이전트가 근거를 찾는 문서 검색(BM25 + 한국어 글자 2-gram, 표준 라이브러리, 사내망 밖으로 아무것도 보내지 않음)이 질문에 맞는 문서를 찾는지 잽니다. 문서 지도의 관계와 달리 "이 질문의 답이 어디 있나"를 봅니다.

<!-- quality-retrieval -->

사람이 묻는 창구는 [문서 지도](../graph/README.md)의 **질문** 칸입니다(개발 미리보기에서, 이 PC의 질문 서버·임베딩·생성 모델로 답하고 문장마다 인용을 점검). 질문 서버는 `.docs-kit/bin/serve.sh ask start`, 임베딩·생성 모델 서버는 프로젝트가 띄웁니다(`docs/quality/config.json`의 `embed_start`, `llm_start`에 시작 명령을 적으면 안내에 나옴). 로컬 임베딩을 더한 효과와 설정 근거는 프로젝트의 검증 기록(VR)에 둡니다.

## 사례 기록

사용자나 점검이 찾아낸, 에이전트가 틀리게 말한 일입니다. 같은 일이 되풀이되지 않도록 원인과 막는 법을 남기고, 그 질문을 검색 평가에 더합니다(`docs/quality/incidents.json`).

## 설정과 파일

| 파일 | 담는 것 |
| --- | --- |
| `docs/quality/config.json` | 외부 저장소·장비 경로(`path_external`, 점검 안 함), 아직 없는 계획 경로(`path_planned`, 확인 못 함으로), 무시할 경로·이름 |
| `docs/quality/questions.json` | 검색 평가 질문과 정답 문서 |
| `docs/quality/history.json` | 날짜별 요약(`python3 .docs-kit/bin/docs_check.py --record`, 주간 보고 때) |
| `docs/quality/incidents.json` | 할루시네이션 사례: 날짜, 누가, 유형, 주장, 사실, 어떻게 알았나, 막는 법 |
